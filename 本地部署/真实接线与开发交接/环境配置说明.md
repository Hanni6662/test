# 本地真实生图与开发交接配置说明

更新日期：2026-10-12。面向本地开发，不作为公网生产部署说明。

## 当前状态与交付范围

当前 Vue → backend → Dify v3.4 → APIMart → backend 私有保存 → Vue 预览/历史/原图下载的真实本地链路已通过。两张图分别只提交一次；修正后的第二个任务完成了 Dify 正常轮询、H6/H7 回传与原图下载。同一访客连续创作已验证，相关后端隔离回归 425 passed。主图加一张辅图的真实分析与取消也已验证。详见本目录当前状态记录；这不代表公网生产、多用户压力或全部八图位的付费验收。

v3.4 指商品视觉工作流的业务版本；当前本机 Dify 软件版本为 1.17.1。两者不是同一个版本号。流程保持一次上传、一轮偏好选择、一次任务级提示词生成，不恢复旧版补问。

期望链路：

```text
Vue → backend 访客与图片上传 → Dify 识图/推荐
    → Vue 一次选择 → backend 保存 Task → Dify 生成完整提示词包
    → backend 返回生成许可 → image-generation 调用 APIMart
    → backend 接收状态、私有保存图片 → Vue 预览、历史、原图下载
```

## 开发包目录与修改边界

共享包将采用以下结构，最终以验收后生成的清单为准：

```text
交付包/
  README.md
  本地部署/                  # Compose 运行配置、启动入口、无密钥模板、版本与验收说明
  images/                   # 固定后端/生图服务镜像及校验值，或固定镜像下载清单
  dify/                     # 无密钥 v3.4 接线 DSL、导入/模型配置说明
  frontend/                 # 可自由修改的 Vue 源码、package-lock.json、API 对接说明
  backend-source/           # 开发需要时提供的清洁源码；不含本地运行数据
```

前端可以独立改页面、样式、组件和交互。后端用户 API 的字段、幂等键、Cookie 会话、原图完整读取、结果未知时禁止重复购买等合同必须保留。参考 `docs/Vue接口对接.md` 和前端 README。调整后端或 Dify 合同时，应同步前端并重新验证相关链路。

后端、生图服务以及 Dify 依赖以容器运行，前端默认本机运行，便于开发。镜像版本必须固定；镜像标签名 `latest` 不作为版本证据。

## 机器环境

- Docker Engine / Docker Desktop，Linux 容器。Windows 推荐 WSL2 后端。
- 前端开发使用 Node.js 22.14 或更新的兼容版本和 npm。
- 可访问 npm 镜像源、所用容器镜像源、分析模型供应商和 APIMart。
- 确认本机端口未被其他项目占用。不要启动同名历史 Compose 栈争抢端口。
- 安装目录可包含中文；使用随包启动脚本，不依赖当前工作目录。

当前本机地址仅供参考：Vue `http://127.0.0.1:5173`，业务 API `http://127.0.0.1:18160`，Dify 控制台 `http://localhost`，生图服务健康检查 `http://127.0.0.1:8091/healthz`。新机器可以调整宿主端口；容器之间使用服务名和容器端口，不能把容器中的 `localhost` 当成宿主机。

## 每个开发人员必须自行提供的凭证

| 凭证 | 配置位置 | 说明 |
|---|---|---|
| 分析模型供应商 API Key | 自己的 Dify 工作区模型供应商 | 不随 DSL 导出，不从原开发者数据库复制 |
| 分析模型 API 地址/模型名 | Dify 模型供应商及 LLM 节点 | 本次目标为 aipaibox、`claude-sonnet-5-5`；需验证实际接口协议与视觉能力 |
| Dify 应用 API Key | 后端的本地私有运行配置 | 在目标 Dify 应用的 API 访问中生成；与模型供应商 Key 不同 |
| APIMart API Key | image-generation 的本地私有运行配置 | 只由生图服务读取，不能进入前端 |
| 数据库/消息队列密码 | 目标机器的初始化配置 | 每次新部署单独生成，不继承原机器密码 |
| Dify 回传认证 secret | Dify 与 backend | 两端相同，至少 32 个非空白 ASCII 字符 |
| 生成许可签名 secret | backend 与 image-generation | 两端相同，独立于回传认证与维护 secret |
| image-generation 服务 Token | Dify、backend、image-generation | 三方对应配置相同，用于服务认证及受控参考图读取 |
| 维护 secret | backend 私有运行配置 | 单独生成，不提供给前端 |

不要把任何 Key 写入 `VITE_*`：这些值可能被构建进浏览器代码。Key 不放入 URL、不通过聊天传递、不提交 Git、不写入测试日志。

## Dify 模型和流程配置

1. 在自己的 Dify 中创建管理员和工作区，配置模型供应商。
2. 导入交付包内标记为真实接线版本的 v3.4 无密钥 DSL。不要导入包含 fake LLM/fake provider 的隔离验收副本。
3. 为 `audit`、`resolve_0`、`design` 选择实际可用模型，核实视觉输入。承担识图的节点必须收到实际主辅图片像素。
4. 填写目标实例的内部环境变量并发布。后端固定记录目标 App ID 与发布 Workflow ID；导入后的 ID 与原机器不同，不能直接复用。
5. 为目标应用生成 Service API Key，保存在 backend 配置。

内部环境变量包括 `IMAGE_SERVICE_URL`、`IMAGE_SERVICE_TOKEN`、`DIFY_FILES_BASE_URL`、`BACKEND_STAGE_EVENT_URL`、`BACKEND_STAGE_EVENT_TOKEN`、`BACKEND_CONTEXT_BASE_URL`、`BACKEND_PROMPT_PACKAGE_URL`、`BACKEND_GENERATION_EVENT_URL`、`BACKEND_GENERATION_RESULT_URL`。生成开关的名称和值以最终验收 DSL 为准；新环境在不确定配置时保持关闭。

模型地址示例仅为本次目标，不表示所有 aipaibox 凭证都支持同一协议。当前已有 Dify 模型登记的是 OpenAI Compatible 地址 `https://api.aipaibox.com/v1`；服务商 Claude Code 文档使用 Anthropic 协议。最终使用方式需以实际验证结果为准，不通过添加 `/v1` 猜测兼容性。

## 后端真实 Chatflow 配置

下列名称来自当前代码，值均须由目标机器提供：

```dotenv
IMAGE_BACKEND_CHATFLOW_HANDOFF_ENABLED=true
IMAGE_BACKEND_CHATFLOW_FLOW_VERSION=visual-v3.4-single-selection
IMAGE_BACKEND_CHATFLOW_DIFY_MODE=http
IMAGE_BACKEND_DIFY_APP_ID=<目标Dify应用ID>
IMAGE_BACKEND_DIFY_WORKFLOW_ID=<目标已发布WorkflowID>
IMAGE_BACKEND_DIFY_REFERENCE_UPLOAD_ENABLED=true
IMAGE_BACKEND_DIFY_REFERENCE_UPLOAD_API_BASE_URL=<容器可访问的Dify API origin>
IMAGE_BACKEND_DIFY_REFERENCE_UPLOAD_API_TOKEN=<目标应用API Key>
IMAGE_BACKEND_DIFY_CALLBACK_SECRET=<独立回传secret>
IMAGE_BACKEND_GENERATION_PERMIT_SECRET=<独立许可secret>
IMAGE_BACKEND_IMAGE_GENERATION_SERVICE_URL=<生图服务容器origin>
IMAGE_BACKEND_IMAGE_GENERATION_SERVICE_TOKEN=<内部服务Token>
IMAGE_BACKEND_IMAGE_GENERATION_SERVICE_AUTHORITY_ID=<目标生图服务authority UUID>
```

authority UUID 从目标生图服务受认证的 `GET /v3/service-authority` 读取；它与该服务持久数据对应，不能从原机器模板复制。配置须注入 API、Worker、Scheduler、Dispatcher 等相关进程，只改 `.env` 而 Compose 未读取对应字段不会生效。

本地仍使用私有 Local 存储和访客 Cookie，不启用登录、充值或扣费。当前代码拒绝 `IMAGE_BACKEND_ALLOW_PAID_CALLS=true`；真实 Chatflow 路线由独立生图服务调用 APIMart，不要将该旧开关随意改为 true，也不要将 standalone 的 mock generation 枚举改为不存在的 real 值。

## image-generation 配置

```dotenv
APIMART_API_KEY=<自己的APIMart Key>
APIMART_BASE_URL=https://api.apimart.ai/v1
IMAGE_SERVICE_TOKEN=<内部服务Token>
IMAGE_SERVICE_GENERATION_PERMIT_SECRET=<与backend相同的许可secret>
IMAGE_SERVICE_REFERENCE_BACKEND_ORIGIN=<固定backend容器origin>
IMAGE_SERVICE_REFERENCE_BACKEND_TOKEN=<与backend服务认证相同的Token>
IMAGE_SERVICE_MAX_ACTIVE_SLOTS=2
```

新接线使用 `/v3/generation-batches`；参考图由服务按授权从固定 backend 读取，不允许浏览器提交任意下载地址。结果保存到私有业务存储后由 backend 交付，不要求前端直接访问生图服务资源链接。

网络需允许生图服务调用 APIMart；不能仅连接无出口的 internal 网络。Dify SSRF 代理只放行必要的内部服务名和端口，保留其他私网限制。Fake-IP 配置仅在实际使用 DNS 代理且验证精确结果域名时设置，不将允许私网作为通用下载配置。

## 新机器启动与验收顺序

1. 校验交付包 SHA-256 和固定镜像清单；导入镜像或从可信镜像源获取固定版本。
2. 使用新的项目名与独立卷初始化数据库、队列、私有存储和内部凭证。
3. 启动 Dify，配置自己的分析 Key，导入无密钥 DSL。
4. 配置 APIMart Key、服务认证和许可；读取目标 App/Workflow/authority ID，更新 backend 配置。
5. 启动完整运行配置，检查各服务健康、内部 DNS/HTTP、认证、数据库迁移版本与挂载权限。
6. 先验收上传、真实识图、推荐和一次表单选择，再以一张图位测试 APIMart 生图。
7. 验证状态推进、后端私有保存、预览、历史和完整原图下载。模型/生图测试会消耗目标开发者自己的额度。
8. 任何未知受理状态沿原请求查询，禁止因为等待超时直接重复购买。

本机真实启动脚本为本目录 `启动本机真实服务.ps1`；真实 overlay 保存在 `本地运行/真实接线-20261012`。共享模板为本目录 `backend.runtime.example.yaml`、`dify.runtime.example.yaml`、`runtime.example.env` 与 `image-generation.example.env`；它们不包含本机凭证，需由接收者配置。原 mock 部署包仍是独立 mock 包，不使用其中旧镜像替代本次修复镜像。

## 无密钥打包规则

采用明确文件白名单构建共享包，禁止压缩整个项目目录。以下内容一律排除：

- 所有实际 `.env`、`instances/`、`.private/`、凭证 JSON、管理员登录信息和原机器应用 Token。
- Dify/PostgreSQL/Redis/RabbitMQ 的数据库或卷、Dify 加密凭证、原机器加密私钥。
- image-generation SQLite、参考图、结果图片、用户会话和业务私有卷。
- `备份/`、`.migration/`、运行日志、临时文件、测试 Cookie、原始请求/响应抓包。
- `node_modules/`、本机缓存和临时诊断数据。

DSL 必须通过 Dify 的无密钥导出或明确清空全部 secret 环境变量，并检查 HTTP 节点没有内联 Key。容器镜像不得通过 `docker commit` 从带运行凭证的容器生成；使用清洁源码构建，并核查镜像层不含 `.env`、数据库、私钥或用户数据。

打包后检查：文件清单、secret 变量占位情况、凭证模式扫描、与本机实际已配置密钥的内存精确匹配检查、镜像构建上下文和层内路径。检查日志仅报告是否发现与文件位置，不打印任何密钥值。另在全新目录/项目中验证无原机器凭证也能初始化并由接收者填入自己的 Key。
