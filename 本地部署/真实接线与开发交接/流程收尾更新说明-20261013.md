# 流程收尾与一键启动增量更新

本次同步生图后的独立收尾观察、图片交付对账和历史补核，并交付新增迁移 `s027_generation_run_closure`。Dify 主线 DSL、提示词、表单和连线保持原样。

## 接收者升级

1. 保存自己的私有配置并备份业务数据库，等待进行中的任务结束。已有实例不要再次 `init`。
2. 导入 `images/local-runtime-images.tar`，把已有实例文件中的 `APP_IMAGE` 以及真实运行配置中的 `REAL_BACKEND_IMAGE` 都更新为 `image-backend:delivery-run-closure-fix-20261013`。使用自己的实例名、凭证、数据卷与网络。
3. 合并更新 `backend.runtime.example.yaml` 和 `dify.runtime.example.yaml` 到自己的 overlay：迁移服务使用当前固定后端镜像；Dify API、Worker 均注入 `WORKFLOW_MAX_EXECUTION_STEPS=1000`。不需要重新导入或发布 DSL。
4. 从包根目录先执行自己的组合配置对应的迁移：

```powershell
docker compose --env-file './本地部署/原图下载修复版-20261012-025431/instances/localimg-dev01.env' --env-file './本地部署/真实接线与开发交接/runtime.env' -p localimg-dev01 -f './本地部署/原图下载修复版-20261012-025431/compose.yaml' -f './本地部署/真实接线与开发交接/backend.runtime.example.yaml' run --rm --no-deps migrate
```

命令中的实例和运行文件必须替换为自己的配置。S027 只新增收尾表，不改写原任务、原图或 Dify 数据。后端完整进程均更新到新镜像后，Scheduler 会按当前 Dify App 和未过期会话自动补核；没有新生图提交。

5. 按 `frontend/README.md` 更新自己的 `workbench.config.local.json`，执行 `启动本地工作台.ps1 -Check` 后启动。环境变量变化需要重建对应容器，不能只执行 Docker restart。

## 一键启动行为

交付版保留接收者路径与实例配置、按依赖分阶段启动、默认复用正常服务、健康与容器间连接检查、前端代理检查、就绪后打开浏览器等功能。没有复制原开发机器的路径或实例设置。

新检查要求 Dify API/Worker 显式配置相同的 800～2000 步预算，本版模板使用 1000；启动后进一步检查实际容器值。旧配置缺少预算时，在重建容器前给出配置错误。

成功退出的初始化容器仅在**镜像 ID 仍匹配当前版本**时复用；镜像升级或同标签重新导入后，迁移和初始化重新执行。这样不会因旧迁移容器曾成功退出而漏掉新版本迁移。相同镜像的重复启动仍不重复初始化。

## 完成信息

会话详情和会话历史新增可选 `completion`：`task_status`、`delivery_status`、`dify_run_status`、`reconciliation_status`、`reason_code`、`confirmed_count`、`closed_at`。

图片全部保存并确认、但 Dify 被停止时，可以同时得到 Task `succeeded`、交付 `confirmed`、Dify `stopped` 与对账 `completed_with_execution_warning`。图片仍可查看和下载；原始执行状态与历史未知 Action 保留。业务会话原 `status` 的交接语义未更改。

观察只使用 Dify Service API 的 GET 详情接口，按 App/Run/Workflow 绑定校验；有界退避且最多 32 次已提交的观察意图。失败或预算耗尽不会触发重复生图，不会将已有图片降级。最后交付尚未确认或资产关联不一致时不提前关闭。
